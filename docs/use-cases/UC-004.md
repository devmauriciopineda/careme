# UC-004 — Registrar un evento clínico

## 1. Identificación

| Campo           | Valor                                               |
| --------------- | --------------------------------------------------- |
| ID              | UC-004                                              |
| Nombre          | Registrar un evento clínico                         |
| Actor principal | Persona que registra su historia clínica            |
| Nivel           | Objetivo de usuario                                 |
| Sistema         | Careme — asistente de historia clínica personal     |
| Prioridad       | Alta — es la entrada del ciclo básico del producto  |
| Estado          | Propuesto                                           |

## 2. Objetivo

Que el usuario deje constancia de un hecho médico contándolo con sus propias
palabras, para que pase a formar parte de su historia clínica y pueda
consultarlo después.

## 3. Precondiciones

- El sistema está disponible.
- El usuario tiene acceso al chat del asistente, que es el punto de entrada del
  producto.
- Existe una sola historia clínica: la del propio usuario. No hay que
  identificarse ni elegir a qué persona pertenece el hecho.
- No se exige que existan eventos previos.

## 4. Disparador

El usuario envía un mensaje en el chat que contiene un hecho médico.

## 5. Flujo principal

1. El usuario cuenta un hecho médico en lenguaje natural.
2. El sistema interpreta el mensaje y determina que contiene un hecho que debe
   quedar registrado.
3. El sistema extrae la información mínima disponible: el tipo de hecho, la
   fecha con su grado de precisión y el contenido con lo que el usuario
   expresó.
4. El sistema comprueba que el hecho puede registrarse y que la información es
   suficiente.
5. El sistema incorpora el hecho a la historia clínica del usuario, conservando
   la precisión temporal que el usuario aportó.
6. El hecho queda disponible de inmediato para futuras consultas.
7. El sistema responde con una confirmación breve que resume el hecho
   registrado.
8. **Resultado:** el usuario sabe que su hecho médico quedó registrado en su
   historia clínica.

> **Alcance del registro desde el chat (UC-013).** Cuando el hecho llega en un
> mensaje del asistente, UC-013 lo recoge primero como nota de la consulta en
> curso y lo registra al cerrarla. La disponibilidad inmediata describe el efecto
> del registro: un hecho puede consultarse en cuanto queda registrado, y no antes.
> Ese camino no añade tipos ni reglas de registro: los tipos admitidos y las
> reglas de este caso de uso siguen aplicando, en el momento del cierre. El
> contenido** puede completarse durante la conversación —preguntando lo que
> falta, ampliando el contexto con lo que ya consta o pidiendo una aclaración—
> sin inventar información, pero el hecho no se incorpora a la historia hasta que
> el cierre lo registra.

## 6. Flujos alternos y excepciones

| Código | Situación                                                                          | Respuesta del sistema                                                                                             |
| ------ | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| A1     | El mensaje expresa una fecha aproximada ("hace unos dos años", "el mes pasado")     | El sistema registra el hecho conservando esa imprecisión y no lo convierte en una fecha exacta.                    |
| A2     | El mensaje no indica ninguna fecha                                                  | El sistema registra el hecho sin fecha, dejando constancia de que se desconoce.                                    |
| A3     | El mensaje usa una expresión temporal relativa ("hoy", "ayer", "hace dos semanas")  | El sistema la resuelve tomando como referencia el día actual y registra el hecho con la fecha resultante.          |
| A4     | El mensaje contiene varios hechos médicos distintos                                 | El sistema registra un evento por cada hecho y lo confirma al usuario.                                             |
| A5     | El mensaje es ambiguo o le falta información para registrar el hecho                | El sistema pide al usuario que aclare antes de registrar nada.                                                     |
| A6     | El mensaje expresa una creencia o sospecha, no un hecho vivido ("creo que podría tener hipertensión") | El sistema no lo registra como hecho y se lo explica al usuario.                                   |
| A7     | El mensaje no contiene ningún hecho médico (conversación general o pregunta)        | El sistema no registra nada y responde con normalidad.                                                             |
| A8     | El usuario vuelve a contar un hecho que ya quedó registrado en la conversación en curso | El sistema reconoce que ya está registrado, no crea un evento duplicado y se lo indica al usuario.                 |
| E1     | El hecho no puede registrarse y el usuario no aporta la aclaración pedida           | El sistema no registra nada y mantiene la historia como estaba.                                                    |
| E2     | El sistema no puede completar el registro                                           | El sistema informa del fallo en el idioma del usuario, no deja ningún registro a medias y ofrece volver a intentarlo. |

## 7. Postcondiciones

- **Éxito:** la historia clínica contiene el nuevo evento, con su tipo, su fecha
  y su grado de precisión y el contenido expresado por el usuario; queda
  disponible para consulta de inmediato.
- **A1, A2, A3:** el evento conserva exactamente la precisión temporal que aportó
  el usuario, sin fechas exactas inventadas.
- **A4:** la historia contiene tantos eventos como hechos distintos contenía el
  mensaje.
- **A5, A6, A7:** no se añade ningún evento a la historia.
- **A8:** no se añade ningún evento nuevo; el hecho ya registrado permanece tal
  como estaba, sin duplicarse.
- **Fallo (E1, E2):** no se añade ningún evento; la historia permanece
  exactamente como estaba antes del mensaje.

## 8. Reglas de negocio

Reglas transversales aplicables —
[`reglas-de-negocio.md`](./reglas-de-negocio.md): RN-005, RN-006, RN-007,
RN-008, RN-018, RN-021, RN-022, RN-023, RN-024, RN-026, RN-029, RN-030.

Reglas propias de este caso de uso:

- Los tipos de evento admitidos son cuatro: diagnóstico, medicación, medición y
  nota.
- Todo evento tiene un tipo, un contenido y una fecha con su grado de precisión;
  la fecha puede faltar cuando el usuario no la indica.
- El contenido conserva los valores tal como los expresó el usuario (por
  ejemplo, una presión de 145/92).
- Solo se registran hechos médicos; las preguntas y la conversación general no
  generan eventos.
- La confirmación al usuario resume el hecho registrado.
- Si el hecho ya quedó registrado en la conversación en curso, el asistente lo
  reconoce a partir de esa conversación y no lo duplica.

## 9. Requisitos no funcionales relevantes

- **Confirmación breve:** tras registrar, el usuario recibe un resumen corto y
  claro del hecho guardado, sin información técnica.
- **Disponibilidad inmediata:** un hecho registrado puede consultarse en cuanto
  se confirma, sin esperas ni acciones adicionales.- **Fidelidad temporal:** una fecha aproximada no se presenta nunca como exacta;
  lo registrado refleja lo que el usuario dijo.
- **No invención:** el sistema no añade datos que el usuario no aportó ni
  completa la información con suposiciones.
- **Aclaración comprensible:** cuando el mensaje es ambiguo, el usuario recibe
  una pregunta clara en su idioma que le permite concretar el hecho.
- **Validación comprensible:** cuando un hecho no puede registrarse, el usuario
  recibe una explicación clara en su idioma, sin detalles internos.
- **Repetición segura:** volver a contar un hecho ya registrado en la misma
  conversación no genera un evento duplicado; el usuario recibe la misma
  confirmación del hecho existente.
- **Resiliencia:** ante un fallo al registrar, el usuario no pierde lo que contó
  y puede volver a intentarlo.
- **Idioma:** los textos visibles para el usuario están en español.

## 10. Fuera de alcance

- Corregir, completar, editar o borrar un evento ya registrado.
- Pedir confirmación obligatoria antes de registrar (el sistema registra
  directamente y luego confirma).
- Adjuntar o interpretar documentos, imágenes, audio o resultados de exámenes.
- Registrar por chat el peso y la circunferencia abdominal, que tienen su propio
  seguimiento.
- Consultar, buscar o preguntar por los eventos registrados (UC-005 a UC-008).
- Múltiples pacientes, cuentas, roles o acceso de terceros.
- Diagnóstico, recomendaciones médicas o detección automática de enfermedades.
- Traducción a otros idiomas en tiempo de ejecución.
